☀ Afternoon

Plateforme de recrutement B2B. Un cabinet (les agents) source des candidats ; une IA lit les CV, et un moteur de matching propose ces candidats aux entreprises clientes (les customers) en fonction de leurs besoins.

Ruby 3.4.2Rails 8.0 HotwireTailwind v4 SidekiqPostgreSQL + pgvector DeepSeekCohere Heroku

1. Vue d'ensemble

Un cabinet de recrutement perd du temps : des CV éparpillés dans des emails, des rapprochements candidat/poste faits à la main, aucune traçabilité côté client. Afternoon industrialise ce pipeline :

  1. L'agent importe un CV (PDF). Une IA (DeepSeek) le lit et remplit automatiquement la fiche candidat.
  2. Quand l'agent publie le candidat, le système calcule sa proximité sémantique avec les projets ouverts (embeddings + pgvector).
  3. Le customer crée un projet (un besoin de poste). Il reçoit des candidats matchés et anonymisés, avec une analyse rédigée par l'IA.
  4. Le customer met les profils intéressants au panier et demande un rendez-vous ; l'agent valide et fait l'intermédiaire jusqu'à l'embauche.
À retenirL'objet central n'est ni le candidat ni le projet, mais le lien entre les deux : ProjectCandidate. C'est lui qui porte le score de matching, l'analyse IA et tout le tunnel « proposé → intéressé → embauché ».

2. Les acteurs

Trois publics, trois espaces (/admin, /agent, /customer), une seule table User.

Agent

Consultant du cabinet (rôles agent_manager / agent_user). Source les candidats, importe les CV, valide les matchings et pousse les profils aux clients.

Customer

Entreprise cliente (rôle customer). Crée des projets, consulte des profils anonymisés, exprime son intérêt, demande des RDV.

Super admin

L'équipe Afternoon (rôle super_admin). Back-office ActiveAdmin. Peut « impersonate » un user pour voir l'app à sa place.

User est une seule table pour tout le monde. La casquette d'un user se lit à deux endroits : son role, ET la clé étrangère par laquelle on l'atteint : agent_id sur un candidat, customer_id sur un projet ou un panier. Toujours regarder la FK pour savoir quel rôle est attendu.

Les modèles à connaître en priorité

Modèle Rôle
User Compte unique : super_admin, agents, customers (distingués par role + FK).
Candidate Profil sourcé par un agent. Deux machines à états (AASM) : import_status et publication_status.
Project Besoin de poste créé par un customer. Peut générer une SavedSearch.

À retenirProjectCandidate n'est pas une simple jointure : c'est un objet riche qui stocke le score de similarité (decimal 0..1) et deux analyses IA (la brute du LLM + celle corrigée par l'agent, qui prime à l'affichage).

6. Le pipeline d'import d'un CV

Une chaîne de jobs Sidekiq asynchrones. Lecture verticale, étape par étape.

Les files d'attente Sidekiq

Queue Poids Pour quoi
default 10 Jobs rapides : update candidat, géocodage, matching, skills.
mailers 5 Emails + tâches cron (digest, expirations de candidats, etc.).
llm 1 Jobs lents qui appellent DeepSeek. Bridés à 2 en parallèle (throttle) pour ne pas exploser le coût/débit.
À retenirTout n'est pas un enchaînement de jobs : des callbacks de modèle (after_commit) amorcent des étapes clés. Pour comprendre « qui déclenche quoi », cherche autant dans les modèles que dans les jobs.

7. L'IA : deux mondes

DeepSeek « comprendre & rédiger »

Un LLM (modèle deepseek-v4-flash). Lit du texte (CV, projet) et renvoie du JSON structuré : extraction de fiche candidat, vérification de publication, analyse candidat×projet (anonymisée), synonymes de compétences.

Cohere « mesurer la ressemblance »

Des embeddings : transforme une phrase en vecteur de 1024 nombres. Deux phrases de sens proche donnent des vecteurs proches. C'est ce qui matche « chef de chantier » avec « conducteur de travaux » sans mots communs. Stocké en pgvector.

Exemple : matching → analyse → notification

La chaîne démarre sur un callback de modèle (after_commit), pas un appel direct ; l'agent est prévenu par email à la fin.
À retenirEmbeddingCache existe pour ne pas repayer Cohere sur les mêmes textes : on hashe le texte, on réutilise le vecteur (cache LRU, 10 000 entrées max). Le LLM, lui, a son propre garde-fou côté import (llm_analysis_result mémorisé pour ne pas rappeler DeepSeek au retry).

8. Le frontend

Server-rendered + Hotwire. Pas de build JS : pas de npm, pas d'esbuild.
  • HTML généré côté serveur (ERB), enrichi par Turbo (navigation, frames, streams) et Stimulus (25 petits contrôleurs JS).
  • JS servi par importmap + propshaft ; libs externes pinnées sur CDN (config/importmap.rb). CSS en Tailwind v4 (config dans le CSS, pas de tailwind.config.js).
  • Classes-composants réutilisables dans app/assets/tailwind/application.css : .button-primary, .card, .title-2… Réutilise-les plutôt que d'empiler des utilitaires.

Le « temps réel » a deux saveurs

WebSocket (broadcast)

turbo_stream_from + Turbo::StreamsChannel.broadcast_replace_to dans les machines à états. Un CV importé en arrière-plan met à jour son badge de statut sans recharger la page de l'agent.

HTTP (réponse ciblée)

render turbo_stream: [...] dans les contrôleurs : une action met à jour plusieurs zones du DOM d'un coup (compteur panier + toast + bouton). Ex. baskets_controller.

À retenirPas de polling, pas de SPA. Tu écris de l'ERB + du Tailwind ; le JS reste de petits contrôleurs Stimulus dans app/javascript/controllers/. Les uploads de CV/avatars vont directement du navigateur vers Cloudinary (ils ne passent pas par le serveur Rails).

git checkout -b feat/ma-feature

10. Lancer en local

Le serveur tourne sur le port 3002, tous les process via Overmind. 
bundle install # installer les dépendances
rails db:create db:migrate # créer la base de données
overmind start -f Procfile.dev   # démarre automatiquement web + sidekiq + css (port 3002)

Commandes utiles : overmind restart web (après un changement de code), overmind restart sidekiq (après un changement de job).

Tests, lint & CI

bundle exec rspec                                   # toute la suite (110 specs)
bundle exec rspec spec/models/candidate_spec.rb:42  # un test precis
  • WebMock coupe le réseau en test : les appels DeepSeek / embeddings sont stubés, pas besoin de vraie clé pour lancer les specs.
  • CI = CircleCI (.circleci/config.yml), pas GitHub Actions. Elle lance uniquement RSpec (+ précompilation des assets) sur Postgres+pgvector et Redis.
  • J'utilise Rubocop pour linter le code.

11. Premier login (admin)

Aucun compte admin par défaut, et l'inscription publique force le rôle customer (users/registrations_controller.rb:15). Le super_admin se crée à la main.

1. Créer un super_admin (console)

bin/rails console
User.create!(
  email: "tonadresse@email.fr",
  password: "motdepasse", password_confirmation: "motdepasse",
  role: :super_admin
)

Devise n'a pas de confirmation d'email (pas de module :confirmable) : le compte marche tout de suite. recruitment_office / company ne sont pas requis pour un super_admin (seuls les agents exigent un cabinet).

2. Comptes de test (agent + customer)

bin/rails matching:seed_test_data

Crée des locations, compétences et candidats publiés, plus deux comptes prêts à l'emploi :

  • agent@test.com / password123 — espace agent
  • customer@test.com / password123 — espace customer

3. Se connecter

  • Connexion : /users/sign_in (port 3002).
  • Back-office admin (ActiveAdmin) : /admin — réservé au super_admin.
  • Espaces applicatifs : /agent et /customer selon le rôle.
AstuceDepuis /admin, un super_admin peut « impersonate » un agent ou un customer (gem pretender) pour voir l'app exactement comme eux, sans leur mot de passe : current_user devient la cible, true_user reste l'admin.

12. Glossaire & repères

Le vocabulaire qui revient partout dans cette app.
Embedding
Représentation d'un texte en vecteur de nombres (ici 1024). Permet de comparer du sens, pas des mots exacts.
pgvector
Extension PostgreSQL qui stocke des vecteurs et calcule des distances (cosinus <=>). Le matching s'appuie dessus.
AASM
Gem de machine à états. Régit import_status et publication_status d'un candidat (transitions publish, expire…).
Actor
Objet métier réutilisable (gem service_actor), dans app/actors/. Ex. Resume::Analyse, Embedding::Create. C'est là que vit la logique lourde.
Hotwire
Turbo + Stimulus. Rendre une app server-rendered réactive sans SPA ni build JS.
Turbo Stream
Fragment de HTML qui met à jour une zone précise du DOM, via WebSocket (broadcast) ou réponse HTTP.
Dyno
Conteneur Heroku qui exécute un process. Ici : web (Puma) et worker (Sidekiq).
Pundit policy
Classe d'autorisation (app/policies/). Décide qui peut show?/edit? un record. Toute action doit appeler authorize ou policy_scope.
Wicked
Gem de formulaires multi-étapes. Utilisée pour les wizards projet (3 étapes) et candidat (9 étapes).
Impersonation
Gem pretender. Un super_admin se connecte « en tant que » un user. current_user = la cible, true_user = l'admin.
Magic-link
URL signée (p/:token, désinscription) qui connecte ou agit sans login. Toute la sécurité tient à la signature du token.
